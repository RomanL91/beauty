# ТЗ: бэкенд, итерация 3 — кабинет мастера

Цель: PWA мастера работает на реальном API (`VITE_REAL_API=auth,master`): мастер входит
через Telegram, видит график дня и заявки, подтверждает и отклоняет их (вместо CLI),
ведёт чаты с клиентами и забирает диалог у администратора. Поручения (`/me/assistant/*`)
ждут ИИ-агента и остаются на моках.

## 0. Решения

1. **Роль мастера (открытый вопрос 5).** Вход — тот же Telegram, учётная запись та же
   (identity). Мастер привязан к странице телефоном владельца: `Master.owner_phone`
   (E.164). Кабинет определяет мастера так: access-токен → телефон учётной записи →
   мастер с этим `owner_phone`. Учётная запись без страницы — 403 `not_a_master`.
   Привязку ставит оператор: `beauty master assign-owner <slug> <телефон>`, демо —
   `beauty seed-demo --owner-phone <телефон>` (`BEAUTY_DEMO_OWNER_PHONE` в compose).
2. **Поручения** выделены в группу контракта `assistant` (тег): кабинет можно
   включить на реальном API, а поручения оставить на моках до агента. В реальной
   сборке без группы `assistant` экран поручений показывает «появится вместе с агентом».
3. **Агент** (следующая итерация) строится на **Hermes + MCP** (решение владельца):
   доработки по итогам спайка — короткие id тикетов, пул экземпляров, меньше вызовов
   LLM на ход.
4. **«Нужны вы» без агента.** Новая заявка — `needs_me: request` (пока мастер не
   ответил); вопрос клиента (текст, голосовое) при `handler = agent` —
   `needs_me: question`: отвечать на свободный текст пока некому, кроме мастера. Ответ
   мастера или решение по заявке снимает признак.
5. **Непрочитанное (вопрос 14).** Счётчик — сообщения клиента после последнего
   прочтения мастером; чтение истории диалога мастером сбрасывает счётчик (как в моках).
   Отдельный `POST …/read` — при необходимости позже.
6. **Поток `/me/events` — живой, без журнала.** Кадры приходят с момента подключения;
   при переподключении с `Last-Event-ID` сервер сразу шлёт `event: reset`, и кабинет
   перечитывает график и чаты (они всегда читаются целиком и дёшево). Журнал как у
   переписки клиента здесь не нужен: кабинет — один пользователь на мастера.
7. **«Предложить другое» (`decline.offer_alternatives`).** После отклонения
   администратор записи присылает клиенту окна на ближайший день той же услуги.
8. **Номер визита** в карточке клиента — завершённые визиты + 1; переписка считает их
   по событиям `booking.appointment.completed`.

## 1. Tenancy

* `Master.owner_phone`, команда `AssignOwner`; запрос `FindMasterByOwner(phone)`.
* `GetMasterPage` для владельца видит и черновик.

## 2. Booking

* `POST /me/appointments/{id}/confirm|decline` — только записи своего мастера
  (чужие — 404); `decline` принимает `offer_alternatives`, `reason`.
* `GET /me/schedule?date=` — `DaySchedule`: неделя (выходные по расписанию и датам),
  записи дня (заявки, подтверждённые, завершённые) с `conversation_id`, перерывы
  (промежутки между рабочими интервалами), свободное время (рабочее минус записи),
  сводка (записи, заявки, свободные минуты). Время — в поясе мастера.

## 3. Conversations

* Переписка хранит то, что видно в списке чатов: снимок клиента (имя, маскированный
  телефон), `handler`, `needs_me`, последнее сообщение, непрочитанное, число визитов.
* `GET /me/conversations?filter&q` (поиск по имени, цифрам телефона и тексту),
  `GET /me/conversations/{id}`, `GET /me/conversations/{id}/messages` (сбрасывает
  непрочитанное), `POST …/messages` (ответ мастера → `handler = master`),
  `PUT …/handler`.
* Изменения сводки — событие `conversations.conversation.changed`.

## 4. Поток кабинета

`GET /me/events` (Bearer): `message.created|updated` с `conversation_id`,
`appointment.updated`, `conversation.updated`. Realtime-мост будит поток по событиям
переписки и записи мастера; данные кадра поток читает запросами (с проверкой, что это
мастер-владелец).

## 5. Фронтенд

* Вход мастера через Telegram (тот же поток, что у клиента), экран «аккаунт не
  привязан к странице мастера» на 403.
* `VITE_REAL_API=auth,master` в docker-сборке кабинета; кадр `reset` → перечитать всё.

## 6. Качество

Unit: сборка дня (перерывы, свободное время, выходной), сводка переписки, фильтры.
Интеграционные: вход мастера, чужой мастер и не-мастер, график, подтверждение из
кабинета с обновлением карточки клиента, ответ мастера и смена обработчика, поиск,
поток кабинета, ответы по схемам контракта.

## Критерии приёмки

`docker compose up` → `http://master.localhost:8080`: вход через Telegram телефоном
владельца; клиент записывается на `alisa.localhost` → заявка появляется в графике и в
чатах без перезагрузки; «Подтвердить» в кабинете → у клиента «Запись подтверждена».

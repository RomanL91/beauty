# ТЗ: бэкенд, итерация 4 — ИИ-агент ресепшна (Hermes + MCP)

Цель: на свободный текст клиента отвечает ИИ-агент мастера. Он консультирует по услугам
и ценам, ищет окна, записывает, показывает и отменяет записи клиента, а если не уверен,
передаёт диалог мастеру. Runtime — Hermes (профиль на мастера, мультиплексор), инструменты —
наш MCP-сервер `beauty-tools` (решение владельца, итерация 3).

Вне итерации: поручения мастера агенту (группа `assistant` — следующая итерация),
расшифровка голосовых (голосовое передаётся мастеру), память о клиенте между визитами.

## 0. Решения по итогам спайка Hermes

1. **Короткий тикет вместо подписанного.** Модель искажала длинный HMAC-тикет (16 из 35
   вызовов отклонены). Теперь тикет — короткий непрозрачный id (`t-7k3m9q2x`), сам тикет
   (мастер, роль, переписка, клиент, срок) хранит бэкенд. MCP проверяет: токен профиля →
   мастер; тикет → тот же мастер, не истёк, роль `front_desk`.
2. **Ответ клиенту — итоговым текстом хода**, а не инструментом `send_message`: на ход
   нужно на один вызов LLM меньше, а пустой ответ модели не теряет сообщение клиента.
3. **Каталог в инструкциях запуска** (услуги с id, цены, длительности, адрес, правила,
   «сейчас» в поясе мастера) — без инструмента `list_services`.
4. **Инструменты ресепшна:** `find_free_slots`, `book_appointment`, `my_appointments`,
   `cancel_appointment`, `handoff_to_master`. Данные других клиентов недоступны
   по построению: клиент берётся из тикета, а не из аргументов.
5. **Передача мастеру.** `handoff_to_master` ставит «нужны вы: вопрос» и оставляет
   мастеру заметку агента (`agent_note` — клиенту не отдаётся никогда). Ошибка или таймаут
   runtime — тоже передача: признак «нужны вы» от вопроса клиента не снимается.
6. **Агент включается по мастеру.** Профиль Hermes создаёт оператор
   (`beauty agent provision <slug>`); без профиля или при `BEAUTY_AGENT__RUNTIME=off`
   свободный текст по-прежнему ждёт мастера. Диалог, который ведёт мастер
   (`handler = master`), агент не трогает.
7. **Сериализация ходов** — на нашей стороне: консьюмер с single active consumer, ход
   ждёт результата запуска.

## 1. Контекст agent (`src/beauty/contexts/agent`)

* `AgentProfile` (мастер → профиль Hermes, ключ Runs API, дайджест MCP-токена, вкл/выкл).
* `RunTicket` (короткий id, мастер, роль, переписка, клиент, срок).
* `AnswerClient` — по событию `conversations.client.message_posted` (текст, голосовое):
  тикет → инструкции → `AgentRuntime.run` → ответ в переписку (`ai_generated`).
* Порт `AgentRuntime`; адаптеры `HermesRuntime` (Runs API: `POST /p/<профиль>/v1/runs`,
  `Idempotency-Key` = id сообщения клиента, опрос статуса) и выключенный.
* Провижининг Hermes (из спайка): шаблон `beauty-template` (модель, тулсеты без
  shell/файлов/браузера, MCP `beauty`), клон на мастера со своими секретами и SOUL.md.

## 2. MCP-сервер `beauty-tools`

Процесс `beauty mcp` (Streamable HTTP, `/mcp`). Аутентификация — `Authorization: Bearer
<MCP-токен профиля>` (+ сверка `X-Hermes-Profile`), авторизация действия — тикет.
Инструменты вызывают команды и запросы контекстов через медиатор.

## 3. Conversations

* `PostAgentReply` — ответ агента (`ai_generated`), снимает «нужны вы: вопрос».
* `HandOffToMaster` — «нужны вы: вопрос» + `agent_note` мастеру.
* `agent_note` не попадает в историю и поток клиента.
* В событии `ClientMessagePosted` — текст сообщения (для агента).

## 4. Инфраструктура

* Настройки `BEAUTY_AGENT__*`: `runtime` (`off|hermes`), адрес Hermes, команда CLI,
  каталог профилей, адрес MCP для Hermes, модель, срок тикета, таймаут хода.
* docker compose: сервисы `hermes` и `mcp` в профиле `agent`
  (`docker compose --profile agent up`).

## 5. Качество

* Unit: тикеты, инструкции, обработчик ответа на двойниках runtime.
* Интеграционные: MCP по HTTP настоящим MCP-клиентом (токен, тикет, чужой мастер,
  истёкший тикет), запись через инструмент, передача мастеру, скрытие `agent_note`.
* Живой прогон: настоящий Hermes в docker со сценарной OpenAI-совместимой «моделью»
  (ключа LLM нет) — ход проходит Hermes → MCP → запись → ответ в чате.

## 6. Итоги живого прогона (2026-10-16)

Стенд: `docker compose --profile agent --profile fake-llm`, настоящий Hermes
(`nousresearch/hermes-agent:stable`, мультиплексор), сценарная «модель»
`devtools/fake_llm.py`. Сценарий «привет → запиши на массаж → есть парковка?»:
ход Hermes 0,6–1,1 с, заявка создана через `book_appointment` (карточка в чате, окно занято
для следующих), вопрос ушёл мастеру `agent_note`, клиент заметку не видит. «Модель»
недоступна → через `run_timeout` заметка мастеру, клиенту ничего.

Найдено и исправлено по ходу:

* **Мост `tool_search`.** Свежий Hermes прячет MCP-инструменты за
  `tool_search / tool_describe / tool_call` — +2 вызова LLM на ход. В шаблоне
  `tools.tool_search.enabled: off`: модель видит `mcp__beauty__*` сразу.
* **Служебный ответ как ответ клиенту.** Если модель промолчала, Hermes завершает ход
  статусом `completed` с текстом «⚠️ No reply: …». `HermesRuntime` считает такой ход
  неудачным (`no_reply`) — диалог уходит мастеру.
* **Ход по таймауту** останавливается в Hermes (`POST …/runs/{id}/stop`), чтобы не держать
  слот `max_concurrent_runs`.
* **Смена шаблона** (`beauty agent bootstrap`) доводит до него и уже созданные профили
  мастеров (их секреты не трогаются).
* **Шаблон в мультиплексоре.** Пока gateway не поднялся, `gateway stop` шаблона не
  срабатывает — `agent-setup` ждёт healthcheck Hermes.
* `httpx` — зависимость рантайма (клиент Hermes), а не только тестов.

Hermes оборачивает результат инструмента в `<untrusted_tool_result>` и кладёт JSON
строкой — модели это не мешает, но разбор в сценарной «модели» это учитывает.
